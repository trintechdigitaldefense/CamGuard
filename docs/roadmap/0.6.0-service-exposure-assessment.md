# CamGuard 0.6.0 — Service Exposure Assessment

## Status

**Milestone:** Proposed for 0.6.0  
**Status:** Design specification; not implemented  
**Scope:** Authorized, bounded, read-only observations of CCTV/IP-camera and NVR network services.

This milestone extends CamGuard's existing private-network TCP reachability observations. It must not be described as a vulnerability scan, proof of compromise, or proof that a device is secure.

## Objective

Give an assessor and business owner a concise, evidence-backed view of which network entry points responded, what service (if any) could be identified, what encryption evidence was observed, why the observation matters, and what action is recommended.

The feature should produce understandable observations without logging in to devices, accessing video, exploiting services, or changing device/network configuration.

## Required observation record

Each observation should be a structured, versioned record with these fields:

| Field | Meaning |
|---|---|
| `schema_version` | Version of the observation schema. |
| `assessment_id` | Identifier linking the observation to one assessment run. |
| `observed_at` | Time the check was performed, with timezone. |
| `asset_id` | Stable assessment-local asset identifier when available. |
| `device_ip` | Approved private IPv4 address checked. |
| `transport` | Transport protocol; initial implementation is TCP only. |
| `port` | TCP port checked. |
| `reachability` | `reachable`, `not_reachable`, or `error`. |
| `service_name` | Positively identified service name, otherwise null/unknown. |
| `service_identification` | `confirmed`, `probable`, or `unknown`. |
| `service_evidence` | Minimal evidence supporting identification, such as protocol response or TLS handshake metadata. Do not store credentials, cookies, tokens, or response bodies. |
| `encryption_status` | `confirmed_tls`, `plaintext_protocol_observed`, `not_observed`, or `unknown`. |
| `encryption_evidence` | What was actually tested and observed; distinguish an attempted TLS handshake from a confirmed encrypted application session. |
| `evidence_confidence` | `high`, `medium`, or `low`, with a reason. |
| `business_significance` | Plain-language explanation of why the observation may matter. |
| `recommended_action` | Specific, proportionate remediation or verification guidance. |
| `limitations` | What the observation does not establish. |

The implementation may add fields, but it must preserve the distinctions above and remain backward-compatible with existing report data where practical.

## Interpretation rules

1. **Reachability is not vulnerability.** A reachable TCP port means only that a connection was established within the configured timeout.
2. **A port number is not service identification.** Port 80, 443, 554, 8000, 8080 or 37777 may suggest a common use, but the port alone must never confirm an application or vendor.
3. **Service identification requires evidence.** Use conservative protocol-level evidence. If the response is ambiguous, record the service as unknown rather than guessing.
4. **Encryption claims must be narrow.** A successful TLS handshake confirms TLS negotiation at that endpoint; it does not prove that every application function or video stream is encrypted. A failed TLS attempt does not prove plaintext service. Record exactly what was tested.
5. **Do not infer internet exposure.** A private-scope scan cannot establish whether a device is reachable from the public internet. Internet exposure remains separately verified, operator-supplied context.
6. **No CVE attribution from an open port.** Service observations do not create device identity, firmware identity, CVE applicability, KEV status, or vulnerability-score uplifts.
7. **No response is not proof of absence.** Firewalls, filtering, rate limits, timeouts and service behavior can affect results.

## Safe collection boundaries

- Require explicit authorization and the existing operator authorization attestation.
- Restrict targets to approved RFC1918 IPv4 scope and enforce existing address, port, timeout and concurrency limits.
- TCP-only in the initial milestone; no UDP, raw sockets, packet capture, stealth, or broad internet scanning.
- Keep probes minimal and read-only. No authentication, credential testing, password guessing, exploitation, fuzzing, state-changing requests, or configuration changes.
- Do not access RTSP streams, video/audio, ONVIF control actions, administrative APIs, or sensitive endpoints.
- Do not follow redirects or submit credentials. Avoid collecting full HTTP bodies, cookies, authorization headers, session identifiers, or personal data.
- Make protocol checks explicit and bounded. Any future HTTP/TLS metadata check must use a documented allowlist and strict response-size/time limits.
- Store only the minimum evidence needed to justify the observation.

## Example business-facing observation

**Device:** `192.168.1.45`  
**Port:** `80/TCP`  
**Reachability:** Reachable  
**Service:** HTTP — confirmed by an HTTP protocol response  
**Encryption:** Plain HTTP response observed on this endpoint; no TLS is provided by this particular observation  
**Confidence:** High for HTTP protocol identification; no conclusion about authentication or exploitability

**Why it matters:** An HTTP management interface may expose administrative traffic without transport encryption to parties able to observe the relevant network path.

**Recommended action:** Confirm that the interface is required, use HTTPS where supported, restrict management access to authorized network segments, and have the administrator verify the device's actual configuration.

This is an illustrative example, not a claim about a real device. A port 80 connection alone must not produce this finding; the HTTP protocol response is the supporting evidence.

## Reporting requirements

Include the following in JSON, Markdown and PDF outputs:

- Device IP, transport and port.
- Reachability result.
- Identified service and identification status.
- Encryption observation and exact evidence boundary.
- Evidence confidence and reason.
- Business significance, recommended action and limitations.
- Assessment timestamp and scope context.

Reports should distinguish **observed facts**, **interpretation**, and **recommended actions**. A service-exposure observation should not silently change the existing CVE risk score. If a separate exposure-priority rating is introduced later, document its methodology and keep it distinct from vulnerability severity.

## CLI and integration direction

The preferred implementation is to extend the existing authorized scan workflow and report model rather than create a competing scanner. A dedicated command may be considered only if it reuses the same scope validation, limits and evidence model.

Potential user-facing terminology:

- **Service exposure observations** — what responded and what could be identified.
- **Encryption indicators** — what protocol-level encryption evidence was observed.
- **Verification required** — facts that cannot be established safely without administrator or technician confirmation.

Do not publish proposed command names as available CLI commands until they are implemented and tested.

## Acceptance criteria

- [ ] Every record validates against a documented schema and includes the required fields.
- [ ] Reachable, not-reachable and error outcomes are distinct.
- [ ] Port-only observations never confirm a service.
- [ ] Ambiguous responses remain unknown rather than guessed.
- [ ] TLS success, plaintext protocol evidence, failed TLS attempts and unknown encryption are represented distinctly.
- [ ] Service observations do not create CVE matches or modify existing CVE/KEV score components.
- [ ] Existing private IPv4 authorization and bounded-scope controls are reused.
- [ ] Tests cover timeouts, refused connections, filtered ports, malformed responses, ambiguous banners, TLS negotiation failures and report escaping.
- [ ] JSON, Markdown and PDF reports show evidence, confidence, significance, actions and limitations.
- [ ] Synthetic tests verify that credentials, cookies, tokens, response bodies and client data are not retained.
- [ ] Existing CLI behavior and current assessment/report tests remain passing.
- [ ] Documentation clearly states that this feature is read-only observation, not a full vulnerability scan.

## Out of scope for 0.6.0

- Camera/NVR login or authenticated configuration inspection.
- Password/default-credential testing.
- RTSP/video access or recording retrieval.
- Exploitation, fuzzing, brute force, or configuration changes.
- Internet-wide scanning or proof of public reachability.
- Automatic CVE attribution based only on port, banner or service name.
- Claims that an unobserved service is absent or that a device is secure.

## Follow-on opportunities

Once service observations are stable, they can feed the technician-assisted inspection workflow, remediation guidance, assessment history and before/after reporting. Those should be separate, versioned milestones with their own evidence and authorization controls.


## Initial implementation notes

The development branch now includes an initial implementation with these deliberately narrow probes:

- TCP reachability outcomes are recorded for every configured port on every address in the authorized scope, including `reachable`, `not_reachable`, and `error`.
- HTTP identification uses a single unauthenticated `HEAD /` request on ports 80 and 8080 and records only the response status line.
- TLS identification attempts a TLS handshake on ports 443 and 8443. It records the negotiated protocol/cipher when available and explicitly states that certificate trust was not evaluated.
- Other ports are recorded as reachable or not reachable but remain unidentified; port-number conventions are hints only.
- The scanner creates a low-severity finding only when it receives a valid HTTP status line over the unencrypted TCP connection. A reachable port by itself does not create a vulnerability finding.
- JSON, Markdown and PDF reports include the service observation fields.

The initial implementation and tests are part of the development pull request, not the current published release. Full repository CI, regression validation and review are still required before merging or releasing.
